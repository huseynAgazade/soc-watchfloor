Authorization is not a prompt.

The tenant argument in every call is overwritten by the server from the session. The model can ask for another customer; it never receives one.

The directory is the source of truth. Nobody appears on a rota, in L1 performance, or in an audit line until they exist here. There is no sign-up page: an admin issues the account with a temporary password, a role, a team grade and a tenant scope, and the person is forced to change the password at first login. Leavers are disabled, never deleted, so old audit records keep resolving to a real name.

Tenants are rows, not constants. Every customer is created here and stored in the portal database. The tenant selector in the toolbar, the SLA page, the scope list on every user and the tenant argument on every MCP call all read from this one table — add a customer once and it appears everywhere, with no deployment.

The SOAR label is the join key. It must match the container label in Splunk SOAR character for character — every SLA figure, case count and status mix for this customer is fetched by that string. The portal validates the label against SOAR before the tenant goes live.

Role, then grant. The role sets what kind of work someone does. Publishing a rota is a separate grant on top, because the two rotas belong to two different teams: an engineer account can push the engineer rota and nothing else, an analyst-side account can push the analyst rota and nothing else. One person can hold both, but it is always an explicit tick, never a side effect of a job title.

Rows marked grant are not implied by the role — they are the per-user tickboxes on the account form. The matrix shows the default state a new account of that role is created with.

One-time codes work offline. TOTP is RFC 6238: a shared secret stored in the portal database plus the current time. No SMS, no email, no vendor, no internet — which is exactly why it suits an on-premise deployment. Any authenticator app the team already has (Aegis, FreeOTP, Google Authenticator, 1Password) enrols by scanning the QR the portal draws locally. Turning it off is a supported configuration, not a hack.

What breaks if you turn it off

Nothing breaks. Enrolled secrets are kept, not deleted, so re-enabling the policy does not force the team to re-enrol. What changes is the login flow: the code step is skipped, and the audit line for every session records mfa=off so a later review can tell which sessions were single-factor. Password rules, lockout and session limits are unaffected.

Every widget is a bound query, not a hard-coded number. A widget renders a metric; a metric declares its source and the query that produces it. Splunk metrics are editable SPL right here — the rest bind to the source that actually holds the data (SOAR containers, the roster list, the detection pipeline). Nothing here lets the model compute a figure: the query computes it deterministically, the model only narrates.
